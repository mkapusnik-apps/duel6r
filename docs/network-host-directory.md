# Host directory and password admission

## Authority and scope

This document owns central listing, browser, and optional password behavior. [Network play](network-play-first-release.md) owns gameplay admission and [trust policy](network-trust-and-abuse-limits.md) owns security boundaries. This is target behavior, not a release-readiness claim.

An active listing is an unexpired registration for a ready player-hosted session or a prepared ready dedicated session, including its zero-occupancy idle state. All active listings means all such registrations in the configured directory, not every game running outside that directory. Listing visibility does not depend on LAN membership or join eligibility. NET-PASS owns the common optional Password procedure for both hosting modes; TRU-PUB owns their common encrypted channel without mandatory gameplay certificates or a proxy. Directory owner authorization is not proof of gameplay endpoint identity. A dedicated service owns its publisher independently of its controller. Hosting kind identifies lifecycle behavior, not a different client security profile.

## Listing lifecycle

- **NET-DIR-001** A player-hosted publisher or dedicated service must automatically register its session only after confirmed readiness. Dedicated readiness must include the prepared nonzero empty session identity before publication or first admission; failed startup must not publish.
- **NET-DIR-002** The directory must include all active listings, including ready dedicated idle sessions, full sessions, Password and No password sessions in either hosting mode, first-round, later-round and summary states.
- **NET-DIR-003** Each listing must identify its nonzero session identity, gameplay endpoint, hosting kind, gameplay mode, current player count, effective player capacity, protection kind, match phase and separate admission availability. Dedicated idle, lobby, first-round and later Started context must not imply closure: active rounds and non-final delays remain Open when otherwise eligible; final outcome closes admission through final delay and summary. Zero occupancy is permitted only for a ready empty dedicated session; player-hosted sessions retain their existing minimum.
- **NET-DIR-004** The directory must expire a listing no later than 60 seconds after its last accepted registration or renewal. Reads must exclude expired listings without waiting for background deletion.
- **NET-DIR-005** A ready player-hosted publisher or dedicated service must attempt renewal at least every 20 seconds while directory contact succeeds. It must submit changed authoritative match phase and admission availability, occupancy, effective capacity or protection metadata within five seconds while contact succeeds, including dedicated idle-to-lobby/ongoing-match and reservation changes.
- **NET-DIR-006** An orderly host/service shutdown or dedicated session end must attempt removal of the old listing. A crash or failed removal must use the same expiry rule. Dedicated End/expiry/restart invalidates old admission identity immediately, independent of removal; a fresh distinct empty session/listing may be published only after cleanup.
- **NET-DIR-007** Only the authorized listing owner must renew, change or remove its listing. The dedicated service owns that authority and its memory-only owner credential, not the controller or guests. Restarted/fresh sessions must not inherit admission authority or identity from an old listing.
- **NET-DIR-008** Registration, renewal, removal, and directory reads must use bounded fields, payloads, result pages, request rates, and work. Browsing must let the user reach every active listing through bounded results rather than silently limiting the directory to one page.

## Browse and connection outcomes

- **NET-DIR-009** `NET-10` must let the user refresh listings and select a session for join setup in `NET-03`. Opening the browser must request current listings.
- **NET-DIR-010** The browser must distinguish loading, available results, empty results, stale results, and directory unavailable. Each read attempt must finish or report unavailable within 10 seconds.
- **NET-DIR-011** While the browser is open, it must request a refresh at least every 20 seconds. Previously successful results older than 30 seconds must remain inspectable as unconfirmed, with joining disabled. A pending refresh must disable browser joining. A failed read must hide cached rows and selected-row details until a successful read restores visible results; starting a retry alone must not restore them. The browser may retain selection identity internally, but successful recovery must not substitute another listing or session.
- **NET-DIR-012** Full, admission-closed and unsupported rows in visible successful results must remain readable with joining disabled and the applicable reason. A Started phase alone must not disable joining when Admission is Open; known later-match details explain next-round participation, not immediate spawn. Age-stale successful results remain inspectable as unconfirmed but require successful refresh before joining. Failed-read and successful-empty states expose no cached row, selected-row detail, row-selection caret or row interaction target. Successful current unselected/empty results have a blank reason line without a replacement instruction. Paging controls are shown only when a previous or next direction exists; otherwise the group is hidden. Pointer, wheel, keyboard and controller input must not activate or traverse hidden row or paging targets. Latest UX owns retained-header inline empty/error presentation, not a complete-grey replacement.
- **NET-DIR-013** A protected eligible listing in either hosting mode must lead to common Password entry in join setup; a No password selection must lead to local setup with Password optional and reachable. Hosting kind, protection, endpoint and expected nonzero session identity must remain bound to the selection. Selection must not reserve a slot or grant controller/participant authority, endpoint trust, reachability, compatibility or admission. The actual host/service must enforce security and admission conditions again.
- **NET-DIR-014** A stale, expired, changed, or unreachable selection must produce an actionable failure without joining a different advertised session silently. The user must be able to edit direct setup or return to the browser and refresh.
- **NET-DIR-015** Directory failure must not end a running hosted/dedicated session or block direct joining or Local Play. A player-host must retain publication feedback/retry without match restart. Dedicated publication failure must be observable to the operator with bounded service-owned retries, not controller publication rights or a required session restart.
- **NET-DIR-016** The browser must state that listing visibility does not guarantee reachability. It must not represent another machine's loopback address or an overlapping private address as verified contact with the advertised host.
- **NET-DIR-017** A host must advertise one concrete non-loopback IPv4 endpoint covered by the ready session, never wildcard `0.0.0.0`.
- **NET-DIR-018** Publication must select the numerically lowest eligible assigned public unicast IPv4 address within ready listening coverage, or the numerically lowest eligible assigned private unicast IPv4 address when no public candidate exists.
- **NET-DIR-019** If no eligible non-loopback publication candidate is available or enumeration fails, the host must report publication unavailable without failing the ready session or blocking direct joining.
- **NET-DIR-020** Each registration, renewal, or publication retry must revalidate the advertised address against current local interface information and ready listening coverage.

NET-DIR-017 through NET-DIR-020 and their local listening-coverage selection apply to player-hosted publication. Dedicated publication uses the operator-configured common-channel endpoint under NET-DIR-024. It does not require automatic local-interface selection, an external frontend, or publication of a private proxy backend.

Wildcard coverage permits candidates on current eligible interfaces. Explicit coverage permits only successfully bound selected addresses. Publication retains one listing and one endpoint per session. Public-address preference is not a reachability test or a NAT rule. A candidate change updates the same owned listing through the existing lifecycle. If no candidate remains, the host must attempt removal of its listing and use the existing expiry rule when removal fails. Loopback-only hosting remains usable through direct same-machine joining but has no directory endpoint.

### Dedicated publication and hosting-aware selection

- **NET-DIR-021** Listing metadata must explicitly identify hosting kind and protection kind. Both player-hosted and dedicated rows must use `none` or `password` consistently with `passwordRequired`. Hosting kind must retain distinct lifecycle meaning without selecting a different encryption profile or conferring gameplay authority through a directory field, offer or client choice.
- **NET-DIR-022** Dedicated rows must be disclosed only to consumers that explicitly advertise support for the mode-aware directory contract. Legacy consumers must receive player-hosted-only results or fail closed. Appending a field that legacy consumers ignore is not safe capability isolation.
- **NET-DIR-023** Mode-aware consumers must reject missing, unknown or inconsistent hosting/protection/phase/identity metadata without connecting or falling back to another admission mode, endpoint or session.
- **NET-DIR-024** A dedicated listing must advertise the operator-configured common-channel endpoint as a valid DNS hostname or concrete non-loopback unicast IPv4 with a valid separate port. It must not advertise loopback, wildcard, directory origin or fictional local interface. It must not require a certificate frontend or proxy to publish or join.

The dedicated advertised address and port are configured independently of the local bind address and port. They must identify the intended connectable common-channel gameplay listener, not the former TLS frontend. Wildcard binding must not supply a wildcard advertisement or invent a locally assigned interface. An advertisement does not prove reachability or authorize NAT, firewall, routing, or automatic port changes. Existing hostname validation and separate port bounds of 1–65535 remain applicable.
- **NET-DIR-025** The dedicated service must own registration, renewal, removal and its memory-only listing-owner credential independently of controller presence. Directory owner authorization must not be treated as proof of the gameplay endpoint identity or confer controller/operator rights on a participant.
- **NET-DIR-026** A prepared ready dedicated idle session must be discoverable with a nonzero session identity, zero participants/players, no controller/round and its effective capacity. It cannot start a match. Zero occupancy is not permitted for an ordinary player-hosted listing.
- **NET-DIR-027** A browser-selected attempt must bind hosting kind, endpoint and expected nonzero session identity before authority allocation and preserve them through offer, confirmation, initial snapshot and reconnect grant. Direct joining remains explicitly unbound and uses the same encrypted channel without a hosting-kind selector.
- **NET-DIR-028** The prepared advertised identity must remain unchanged through first committed admission, lobby, gameplay, results, reservations and same-session Return to lobby. Exactly the first committed admission is controller; concurrent later committed admissions are guests. Listings, offers and selection grant no authority.
- **NET-DIR-029** End, controller expiry and restart must invalidate old identity immediately before directory removal finishes. Fresh distinct empty session/listing preparation must follow cleanup. Old and new rows may coexist after lost removal, but old selections must reject before authority allocation without redirection to the fresh session.
- **NET-DIR-030** Occupancy and effective capacity must derive from authoritative retained player/admission state, including reserved players and admitted Waiting slots. Waiting retains ownership/capacity without current-round participation under NET-ADM-014. Selection must not reserve capacity. Actual authority must recheck capacity and admission availability; historical results are not current occupancy.
- **NET-DIR-031** Dedicated publication failure must be observable to the operator. Service-owned retry/removal must remain bounded, use the existing lease/expiry rules and preserve session/direct/Local Play independence without session restart or controller publication authority.
- **NET-DIR-032** All supported client platforms must apply the same join-eligibility rules to both hosting kinds. Linux AArch64/Pi 5 and experimental Apple Silicon macOS 14+ clients must permit dedicated Password and No password setup when otherwise eligible. A dedicated label alone must not disable joining or Password entry.
- **NET-DIR-033** Passwords, reusable proofs, listing-owner tokens and reconnect credentials must never appear in public listing metadata.

An idle selection may become lobby or first-round while join setup is open. The actual service determines the admitted role and destination for the same bound identity. Browser setup must not overwrite its bound endpoint; a changed selection/endpoint requires refresh, or an explicit unbound Direct transition that clears binding and secrets. This contract specifies capability isolation and validation behavior, not a new protocol constant or capability spelling.

The common protection values are an atomic update of the unreleased `/v2/listings` / `mixed-v2` contract and its `m2_` cursor scope. No v3 endpoint or compatibility adapter is required. `/v1/listings` remains player-hosted-only. Retired `invite` records or unknown protection must be safely excluded or fail closed, never relabeled or reinterpreted as password or unlocked admission. Existing 60-second lease expiry handles obsolete records without a running database migration. This contract authorizes no live directory deployment.

## Optional password

- **NET-PASS-001** Both hosting modes must support no password or a non-empty password selected before startup. Player-hosted setup must default to no password and keep the password fixed until that session ends. Dedicated operator configuration must keep its password fixed for the running service under NET-PASS-014 through NET-PASS-016.
- **NET-PASS-002** The actual host or dedicated service must enforce its configured password before committing initial admission for both direct and browser-selected connections. Missing or incorrect passwords must not allocate admitted players or grant participant authority. No password operation must retain every other security, compatibility, capacity and ownership condition.
- **NET-PASS-003** Both hosting modes must provide common Password entry and correction before Connect, retaining endpoint, selected binding and local-player setup after initial password rejection. A protected browser selection must initially focus Password and block an empty submission. A No password selection must initially focus local setup while keeping Password optional and reachable. Direct setup with unknown protection must permit empty Password. Password entry time must not consume the connection deadline.
- **NET-PASS-004** Password rejection must use `Connection not authorized.` without echoing the submitted secret. The user must be able to return to editable join setup.
- **NET-PASS-005** Passwords, reusable password proofs, and listing-owner or reconnect credentials must not appear in directory results, process arguments, logs, diagnostics, crash messages, or persistent player data.
- **NET-PASS-006** Initial password checks must retain bounded admission attempts and non-disclosing failures. A directory lock indication must not replace host enforcement. A password must not grant host authority or control of another participant's players.
- **NET-PASS-007** A valid reconnect in either hosting mode must restore only the existing reserved identity and state through its scoped reconnect credential. Securely erasable password state may be retained only as needed to establish the secure channel; it must not replace the reconnect credential, become a new initial password admission, grant migration or create a fresh player spawn.
- **NET-PASS-008** Password and credential exchanges must use maintained secure mechanisms that protect secrets against passive interception and reject replay.
- **NET-PASS-009** Password-protected admission must protect the password and reusable admission credentials against an active intermediary that does not know the password. A secure exchange must not silently fall back to unprotected password transmission.
- **NET-PASS-010** An unlocked connection in either hosting kind must encrypt credential exchange, but it need not authenticate first contact against an active intermediary. The product must disclose this limitation in its network security guidance for Direct and browser joining. The product must not describe encryption, a listing, or session-ID equality as authenticated server identity. The product must not require gameplay certificate enrollment, a certificate frontend, a pin, or a trust prompt for either hosting kind.
- **NET-PASS-011** Both hosting modes must accept an empty password or a case-sensitive, well-formed UTF-8 password of at most 128 bytes. Passwords must reject code points U+0000 through U+001F and U+007F through U+009F. Spaces, including leading and trailing spaces, must remain valid and must be preserved exactly. The application must not trim, normalize, case-fold or truncate the password.
- **NET-PASS-012** The password editor must validate each typing or paste event as one complete insertion. If that insertion would produce invalid UTF-8, a prohibited control character or an overlength password, the editor must reject the whole event and keep the previous value unchanged. The editor must provide non-secret rejection feedback. A rejected event must not create a sticky invalid state. Subsequent valid input must use the ordinary password procedure.
- **NET-PASS-013** Both hosting modes must use the same password correction and retention rules. Cancel, Edit setup and initial password rejection must preserve editable correction in the same context. Endpoint or port changes, hosting-mode changes, a new listing/session selection and explicit unbound Direct transition must erase the old context’s password. After complete confirmed admission, the application must erase the editable UI password buffer and retain only securely erasable state needed for the established connection and reserved reconnect. Final Leave, End, terminal reconnect failure, context disposal and shutdown must erase that retained state.
- **NET-PASS-014** The dedicated operator may supply a protected local password file through --password-file. No password file must select no-password operation. A valid empty file must also select no-password operation.
- **NET-PASS-015** The service must validate and load the configured password file once before readiness or publication. Unreadable, insecurely protected, invalid UTF-8, control-containing, NUL-containing or overlength content must fail startup without fallback to no-password operation.
- **NET-PASS-016** Dedicated password configuration must persist across fresh sessions within the running service. Replacement must take effect through an operator-controlled service restart, invalidate ended-session identities and reconnect credentials, and require no client release. The controller must not manage the operator password.
- **NET-PASS-017** Password exchange must retain maintained secure mechanisms and must not place a raw password or reusable password proof in a gameplay application frame. Password values must not enter process arguments, environment variables, directory results, logs, diagnostics, crash messages or persistent player data. The operator-managed protected file is the limited server-configuration persistence exception; runtime storage must retain secure erasure.
- **NET-PASS-018** Dedicated operation must reject the retired --invite-file option and must not accept the retired invitation protocol as password admission or an authentication fallback.

An explicitly entered non-empty password must always be honored, including when a listing says No password. It must not be discarded, replaced by the public unlocked PAKE value or automatically retried as unlocked; a mismatch uses `Connection not authorized.` A rejected insertion leaves an existing valid password eligible whenever the ordinary endpoint, local-player and selected-binding checks pass. The retired invitation's sticky invalid history and ASCII/no-space bounds do not apply to Password.

## Support boundaries

LAN is the supported gameplay environment. Valid public IPv4 endpoints are permitted, but the product does not guarantee Internet connectivity, latency, NAT traversal, or protection against every Internet threat. Private-address filtering is not a substitute for password and credential protection. Passwords do not establish personal identity or provide anti-cheat guarantees. Any peer that knows the shared password can act as a password holder; this is not named-server or operator authentication.

Unlocked joining in either hosting kind protects against passive interception, not an active intermediary during first contact. A session identity check does not establish cryptographic host identity. This limitation does not waive listing-owner authorization, certificate-verified directory HTTPS, password-protected admission, or reconnect scope and replay checks. Browser selection does not remove this limitation. Accounts, manual fingerprint comparison, and out-of-band key verification are not required user journeys. The common current player-hosted EC-JPAKE profile is the only gameplay connection profile; failure must not trigger a legacy outer-TLS attempt, plaintext, or a retry with a different password.

The directory deployment section below authorizes only the specified cloud directory environments and their required provisioning. It supersedes earlier blanket cloud-deployment prohibitions for these environments only. It does not authorize cloud gameplay hosting or player accounts. Local Play must not contact the directory.

## Directory deployment

This section owns the operational product contract for the staging and production directory. It records approved deployment constraints, not a claim that either environment is deployed or verified. Player-hosted gameplay, admission, directory behavior, and security requirements remain unchanged.

- **NET-DIR-DEP-001** The directory deployments must use Cloud Run in project `duel-6-reloaded` and region `europe-west1`.
- **NET-DIR-DEP-002** A successful nightly must deploy its directory image to `staging-directory`.
- **NET-DIR-DEP-003** A push to `master` must deploy the same immutable image from the last successfully verified staging deployment to the production directory.
- **NET-DIR-DEP-004** Production promotion must not rebuild the image.
- **NET-DIR-DEP-005** Both directory services must provide public HTTPS access without removing the existing listing-owner authorization requirements.
- **NET-DIR-DEP-006** Staging and production must use separate named Firestore databases and separate runtime identities.
- **NET-DIR-DEP-007** Each directory service must use a minimum of zero instances, a maximum of two instances, and a concurrency limit of 32.
- **NET-DIR-DEP-008** The staging directory must provide HTTPS directory access at `https://staging.duel.netusite.cz`.
- **NET-DIR-DEP-009** The production directory must provide HTTPS directory access at `https://duel.netusite.cz`.
- **NET-DIR-DEP-010** A network-capable nightly client distribution must use the compiled default origin `https://staging.duel.netusite.cz` when `D6R_DIRECTORY_URL` is absent.
- **NET-DIR-DEP-011** A network-capable release client distribution must use the compiled default origin `https://duel.netusite.cz` when `D6R_DIRECTORY_URL` is absent.
- **NET-DIR-DEP-012** The client must use a valid explicit `D6R_DIRECTORY_URL` setting instead of the compiled default. The client must treat a present empty or invalid setting as directory unavailable without fallback to the compiled default.
- **NET-DIR-DEP-013** Distribution workflows must select the compiled default origin by distribution channel independently of the CMake build optimization configuration. An unchannelled build must have no compiled default origin.

A failed or unverified staging deployment is not eligible for production promotion. If no successfully verified staging image exists, there is no eligible image to promote. Public HTTPS directory access does not establish public gameplay reachability or overall network-release readiness.

The nightly distribution path selects staging. The release distribution path selects production, including a manual invocation of the release workflow. `Release` optimization does not identify the release distribution channel. Network-capable macOS distributions follow these same channel rules under [MAC-NET-016](macos.md#network-entry); unchannelled builds have no default origin. This requirement does not add a macOS caller to the existing release workflow or authorize a new cloud deployment campaign.

The client must not switch between staging and production after a directory failure. Explicit overrides must retain the existing origin validation and HTTPS certificate-chain and hostname verification. The explicit loopback-HTTP development exception remains limited to local development. A missing origin in an unchannelled build means directory unavailable. These outcomes must preserve NET-DIR-015 and Local Play independence. Local Play must not contact the directory.

### Directory deployment acceptance criteria

- **NET-DIR-DEP-AC-001 — Staging:** A successful nightly deploys its identifiable immutable directory image to `staging-directory` in the approved project and region. A failed nightly does not qualify for this deployment path. This criterion covers NET-DIR-DEP-001 and NET-DIR-DEP-002.
- **NET-DIR-DEP-AC-002 — Promotion:** A push to `master` deploys the exact image digest from the last successfully verified staging deployment without a rebuild. Failed or unverified staging deployments cannot replace the eligible image. No promotion occurs when no eligible image exists. This criterion covers NET-DIR-DEP-003 and NET-DIR-DEP-004.
- **NET-DIR-DEP-AC-003 — Environment boundaries:** Both services provide public HTTPS directory access and retain listing-owner authorization. The services use separate named Firestore databases and runtime identities, with the instance and concurrency limits from NET-DIR-DEP-007. This criterion covers NET-DIR-DEP-001 and NET-DIR-DEP-005 through NET-DIR-DEP-007.
- **NET-DIR-DEP-AC-004 — Scope and independence:** Deployment instructions distinguish directory availability from gameplay reachability and network-release readiness. The domain and distribution-default changes preserve UI contracts, gameplay admission, direct joining, running hosted sessions, and platform evidence requirements. Local Play does not contact the directory. Experimental macOS follows the same channel rules; native automated directory/package verification is required after integration in `Develop - Sanity` under MAC-NET-AC-004 and gates `sanity` and nightly publication, not pre-review or merge. Actual Mac GUI and live cross-OS checks remain deferred after merge/nightly under MAC-NET-AC-006. No new cloud campaign is required by this platform extension.
- **NET-DIR-DEP-AC-005 — Domain access:** Each approved domain provides certificate-validated HTTPS directory access to its corresponding environment. Domain access retains listing-owner authorization and staging/production isolation. This criterion covers NET-DIR-DEP-008 and NET-DIR-DEP-009.
- **NET-DIR-DEP-AC-006 — Distribution defaults:** With `D6R_DIRECTORY_URL` absent, network-capable nightly packages select the compiled staging origin and release packages select the compiled production origin. Manual release-workflow invocation selects production. Distribution-channel selection remains independent of CMake build optimization configuration. Unchannelled builds have no compiled default origin. This criterion covers NET-DIR-DEP-010, NET-DIR-DEP-011, and NET-DIR-DEP-013.
- **NET-DIR-DEP-AC-007 — Explicit override:** A valid explicit `D6R_DIRECTORY_URL` setting selects the requested directory instead of the compiled default. A present empty or invalid setting makes the directory unavailable without fallback. Directory failure does not switch between staging and production. Existing secure-origin validation and the explicit local-development exception remain unchanged. This criterion covers NET-DIR-DEP-012.

Deployment evidence must identify the immutable source checkpoint, nightly or promotion event, image digest, deployed service revision, project, region, endpoint, and verification result. Promotion evidence must identify the eligible staging deployment and show digest equality with production. Hosted observations must establish HTTPS directory operation and retained listing-owner authorization; emulator results alone do not establish these outcomes. Configuration and access-policy evidence must establish environment separation and service limits. Team supplies this evidence; these criteria do not require a new gameplay or screenshot campaign.

Domain-access evidence must identify each approved origin, its environment and serving service revision, and its certificate-validated HTTPS directory and owner-authorization results. A configured domain mapping alone does not establish DNS resolution or public TLS readiness. Distribution-default and override evidence must identify the immutable client source checkpoint, package identity, distribution channel, build optimization configuration, override presence and validity, and selected origin or unavailable outcome. Relevant consumer results must establish selection behavior and independence; configuration review may support workflow channel selection. These criteria do not require another full gameplay or screenshot campaign.

## Acceptance criteria

- **NET-DIR-AC-001 — Complete listing lifecycle:** Only ready player-hosted publishers or dedicated services register. Prepared dedicated idle, full, protected, running and summary sessions remain listed with authoritative phase and separate availability, including Started/Open and completed/Closed. Final outcome, not first outcome, closes admission. Changed metadata is submitted within five seconds. Shutdown/session end attempts removal; missed removal and crashes expire within 60 seconds without background deletion. Dedicated old identity is invalid immediately and a distinct ready empty identity/listing follows cleanup.
- **NET-DIR-AC-002 — Browser freshness and read outcomes:** Opening, periodic refresh, manual refresh, successful results, successful empty results, age-stale results and failed reads follow the existing 10/20/30-second bounds. Pending refresh cannot initiate browser joining. Age-stale successful rows remain inspectable as unconfirmed, with Join disabled. Failed reads hide cached rows and selected details; successful empty results expose no selection caret or row actions. A retry does not resurrect hidden cache before success. Recovery restores a retained selection only when the same listing/session identity is present and its existing binding remains valid; an absent or changed identity is not replaced automatically. Paging remains available for actual previous/next directions and is hidden when neither exists. Hidden rows and paging controls have no input targets. Full, closed, unsupported and stale rows cannot join.
- **NET-DIR-AC-003 — Real joining:** An eligible player-hosted or dedicated selection reaches its actual secure admission engine and authority-confirmed lobby, immediate first-round or Waiting/next-eligible-round destination for the bound identity. Later Started/Open remains joinable; final-outcome races close admission. Unreachable, expired, wrong-session, ended/restarted, incompatible, full and closed selections fail truthfully before inappropriate authority allocation, without silent substitution.
- **NET-DIR-AC-004 — Independence:** A directory outage preserves an active hosted/dedicated match, direct joining and offline Local Play. Bounded publication recovery does not restart the session; dedicated failure is operator-observable and grants no controller publication actions.
- **NET-DIR-AC-005 — Ownership and limits:** Unauthorized registration-lifecycle changes fail. Service-owned credentials remain separate from controller/gameplay authority and disclose no secrets. Malformed, oversized and excessive requests fail within documented bounds. Lost acknowledgements/removal, revisions, expiry and fresh session ownership cannot resurrect old admission identity or compromise current authority.
- **NET-DIR-AC-006 — Listening coverage publication:** Player-hosted wildcard and explicit-subset sessions publish the deterministic concrete endpoint in NET-DIR-017 through NET-DIR-020. A player-hosted listing never contains `0.0.0.0`, loopback, or an address outside ready listening coverage. No candidate or enumeration failure reports publication unavailable while the session and direct joining remain available. Renewals revalidate candidates and update or remove the same owned listing without creating duplicate sessions. Dedicated common-channel endpoint publication is governed separately by NET-DIR-024 and NET-DIR-AC-008.
- **NET-DIR-AC-007 — Dedicated authoritative listing lifecycle:** A ready dedicated idle session is discoverable at zero occupancy with its nonzero identity/effective capacity and cannot Start. First committed admission preserves that identity and assigns one controller; hosted solo/ongoing rules then apply. Current phase, separate availability, retained/reserved/Waiting occupancy and capacity follow authority through lobby, active/non-final phases, final closure, results, controller reservation and same-session Return. Dedicated controller End/Leave/expiry ends the session. Service publication remains independently owned and bounded. This criterion covers NET-DIR-001–007/015 and NET-DIR-025–026/028–031.
- **NET-DIR-AC-008 — Mixed hosting and common security:** Both hosting kinds expose consistent Password or No password metadata while binding hosting kind and selected endpoint/session. Both use the same encrypted EC-JPAKE channel without a certificate frontend or security selector. Listings disclose no secrets and do not establish authenticated server identity. Legacy v1 remains player-hosted-only; retired Invite/unknown/inconsistent metadata rejects or is safely excluded without reinterpretation. All supported clients, including Mac/Pi, can enter eligible dedicated setup. Full, closed, stale, or otherwise ineligible selections remain disabled. This criterion covers NET-DIR-013 and NET-DIR-021–024/027/032–033.
- **NET-DIR-AC-009 — Selection, concurrency and reuse:** Stale, wrong, ended or restarted selected identities reject before authority allocation without redirection. Concurrent first joins to one advertised empty identity produce exactly one committed controller. End/expiry/restart invalidates that identity immediately; after cleanup a refreshed listing identifies a distinct empty session. Lost removal may leave both rows visible without making the old row admissible. Offers/selection do not reserve capacity or grant authority, and idle-to-lobby/first-round changes use actual authoritative role/destination. This criterion covers NET-DIR-007/013–014 and NET-DIR-026–030.
- **NET-PASS-AC-001 — Host enforcement:** In both hosting modes, no-password admission and correct-password admission succeed when otherwise eligible. Missing and wrong configured passwords fail on direct and browser paths before commitment. An explicit non-empty value for No password is honored and never silently retried unlocked. Correction retains the same permitted setup and binding. Both use the same configured secure profile without a certificate requirement or automatic legacy retry.
- **NET-PASS-AC-002 — Secret protection:** Reviewer evidence establishes the maintained current player-hosted EC-JPAKE mechanism, encrypted exchange, replay rejection and actual host/service enforcement in both modes. No raw password or reusable password proof enters a gameplay application frame. The common unlocked first-contact limitation is disclosed for both hosting kinds and both entry routes without an authenticated-identity claim. Behavioral evidence covers rejected replay, tampering, bounded guessing, and no weaker or legacy-channel retry; arguments, environment variables, listings, diagnostics and player persistence disclose no secrets. Only the protected operator file is an approved server-configuration persistence exception.
- **NET-PASS-AC-003 — Reconnect:** Either hosting mode restores only the reserved participant and current player state through the existing scoped reconnect rules and original deadline. Retained zeroizable password state is used only for the secure channel, not initial admission, new spawning or migration, and is erased at final disposal.
- **NET-PASS-AC-004 — Dedicated operator configuration:** Absence of a password file and a valid empty file select common-channel No password operation. A valid protected file preserves the exact configured password; invalid permissions, missing/unreadable files, malformed UTF-8, prohibited controls, NUL and overlength data fail before readiness/publication without unlocked fallback. Configuration remains static across fresh service sessions; an operator restart applies replacement and invalidates old session/reconnect scope without a client release. Controllers cannot set the operator password. Retired options and invitation protocol/metadata are rejected or safely excluded, never treated as password admission. This criterion covers NET-PASS-014–018.
- **NET-PASS-AC-005 — Common password input and context:** Direct and browser Password/No password paths preserve case, valid UTF-8, spaces and the 128-byte bound.
